## Reflection

### 1. What went well during this unit?

Our group met like usual this week, and getting started felt really smooth. We did a good job splitting up early tasks so everyone had clear ownership, and that helped us keep momentum right away. Some teammates also met outside our main meeting to walk through Material UI setup together, which made frontend setup a lot easier for the team overall. We also stayed organized with our board and milestone tracking, so project management felt much more under control this unit.

### 2. What were some challenges your group faced in this unit?

We did not run into any major blockers, but we did spend time figuring out how to scope our tasks in the best way. A big challenge was deciding when an issue should stay broad as a feature and when it should be broken down into smaller tasks. That came up a lot for backend and data work, where dependencies are not always obvious at first. Even though it was not a huge problem, it was something we had to be thoughtful about as a team.

### Did you finish all of your tasks in your sprint plan for this week? If you did not finish all of the planned tasks, how would you prioritize the remaining tasks on your list?

We finished the main Unit 7 sprint goals we planned for, especially around project setup and organization. Most feature-heavy implementation was intentionally planned for later milestones, so the remaining work is expected carryover and not really missed work. For prioritization, we plan to split the features up according to individual members' interest and time commitment such that no member is fully dependent on the other for a given milestone, which will make it easier for team members to work in parallel.

### Which features and user stories would you consider “at risk”? How will you change your plan if those items remain “at risk”?

The most at-risk features are the ones that depend on both frontend and backend being in sync, like earning coins while working, table integration across core data models, and the user profile flow. These are riskier because they rely on multiple moving parts like API routes, schema decisions, and coordinated implementation. If these stay at risk, we will split them into smaller vertical slices, agree on API contracts first, and focus on shipping core functionality before polish. We can also push some non-blocking visual enhancements later if needed so we protect the main user flow.

### 5. What additional support will you need in upcoming units as you continue to work on your final project?

Ongoing feedback during development would be super helpful for our team. More perspectives on what is working well and what feels unclear would help us make better decisions earlier and avoid rework later. We would especially benefit from feedback on app flow, backend structure, and feature usability as we start integrating everything. Having that support while we are still building will make it easier to improve quality before final submission.
